# Запланировано: цифровая подпись релизов WB (.wbpkg)

**Статус:** отложено, не реализовано.  
**Предлагаемый первый выпуск:** после `v0.2.15`, ориентировочно `v0.2.16` (версия определяется отдельно при выпуске).  
**Основной репозиторий:** `wb.update`.  
**Связанный план:** [PLANNED-UI-UPDATE.md](PLANNED-UI-UPDATE.md).

## Цель и модель угроз

Обеспечить проверку **подлинности и целостности** скачанного `.wbpkg` до исполнения любого кода из него, остановки сервера или прошивки ESP32-S3.

Защищаемся от подмены файла в сети, на сервере загрузки или в GitHub Release **при условии, что приватный ключ подписи не скомпрометирован**. Не ставим целью защиту от физического доступа к microSD Raspberry Pi, от злоумышленника с root-доступом на приборе или от полностью скомпрометированной доверенной системы сборки/подписи. Это сознательная граница защиты, а не гарантия от всех атак.

## Принцип доверия

**Недопустимо** считать безопасной проверку, когда скачанный `.wbpkg` сам запускает свой `verify` и сам содержит единственный доверенный публичный ключ: атакующий может подменить пакет, ключ и проверяющий код одновременно.

- Проверяющий код должен быть **установлен заранее на Raspberry Pi** и запускаться независимо от скачанного пакета.
- Доверенные публичные ключи устанавливаются отдельно от пакета, например в `/etc/wb-update/trusted-keys/`, с правами root; скачанный пакет не может сам объявить свой ключ доверенным.
- До успешной внешней проверки **не импортировать, не распаковывать для исполнения и не запускать** код из `.wbpkg`.
- Для обновления из UI и ручной установки использовать **один и тот же доверенный путь проверки**. Нельзя допускать обхода через `sudo python3 downloaded.wbpkg install` в обычном сценарии.
- Не обещать защиту от root или офлайн-модификации microSD: при такой модели доверенный код/ключ можно заменить.

## Формат подписи

Использовать **Ed25519** и проверенную криптографическую библиотеку, без собственной реализации алгоритма.

Предпочтительный простой формат: GitHub Release содержит два отдельных файла:
- `wb-VERSION.wbpkg` — текущий самодостаточный ZIP-приложение;
- `wb-VERSION.wbpkg.sig` — отсоединённая подпись **точных байтов всего `.wbpkg`**, с явно определённым форматом (например, версия схемы, идентификатор ключа и Base64 подписи).

При проверке дополнительно сверять ожидаемую версию, имя, совместимость с платой, состав и SHA-256 по `manifest.json`. Подпись всего файла предотвращает незаметную подмену также `__main__.py` и установщика. Существующий `packager/build.py verify` оставить как проверку внутренней целостности, но **не называть его проверкой подлинности**.

## Управление ключами

- Создать документированную одноразовую процедуру генерации Ed25519-ключей и безопасной передачи **только публичного** ключа на приборы.
- Приватный ключ **никогда не коммитить** в репозиторий и не включать в пакет, образ SD или логи.
- Описать хранение, резервное копирование, доступ и восстановление приватного ключа.
- Отдельно решить модель подписи: предпочтительнее изолированный процесс/сервис подписи после сборки. Если для первой версии выбран GitHub Actions Secret, явно задокументировать, что компрометация workflow, runner или секретов может позволить выпуск вредоносного **валидно подписанного** пакета. Ограничить доступ к секрету, защищать теги и окружение публикации.
- Поддержать несколько заранее доверенных ключей для ротации. Новый ключ распространять через **уже доверенный канал** и подтверждённую процедуру, а не через непроверенный пакет.
- Описать отзыв/замену скомпрометированного ключа и аварийное восстановление. Не считать отзыв возможным без доставки обновлённого набора доверенных ключей.

## Изменения в wb.update

1. Добавить отдельную CLI-команду/утилиту доверенной проверки, установленную на Pi вне скачанного архива. На вход: путь к пакету, путь к подписи, доверенное хранилище ключей и (при наличии) ожидаемая версия/идентификатор релиза.
2. Проверять подпись **до** выполнения каких-либо инструкций из пакета. Затем проверять внутреннюю целостность, целевую платформу и версию.
3. Исключить TOCTOU: проверять и устанавливать **те же неизменяемые байты** (например, скопировать пакет в root-owned staging с безопасными правами и использовать его после проверки; исключить возможность подмены между проверкой и запуском).
4. Интегрировать с существующей логикой установки `installer/install.py`, не дублировать установку Java/UI/прошивки, резервирование и rollback.
5. Разделить пользовательскую команду доверенной установки и низкоуровневый исполнитель. Удалить `--allow-unsigned` из **штатного** пути; если оставить аварийный обход, сделать его отдельной явной root-only офлайн-процедурой, недоступной через UI и не запускаемой случайно.
6. Не допускать произвольных shell-команд и произвольной замены trust store со стороны веб-приложения.
7. Учесть первичную установку доверенного проверяющего кода и ключа на уже развёрнутые приборы: **bootstrap доверия нельзя обеспечить одним неподписанным скачанным пакетом**. Нужна отдельная контролируемая начальная установка/проверка отпечатка ключа.
8. Документировать процедуру ручной установки подписанного релиза на Pi, без исполнения `.wbpkg` до внешней проверки.

## CI и выпуск

- Сохранить существующую политику `Release.md`: сборка только по новому тегу, точные SHA компонентов, без перезаписи опубликованного релиза.
- Сначала собрать `.wbpkg`, выполнить тесты и внутреннюю проверку, затем подписать **окончательные байты**, после чего опубликовать пакет и подпись вместе.
- Не изменять файл после подписи.
- При ошибке подписи **не публиковать** неподписанный релиз как успешный.
- Включить проверку подписи независимой утилитой в CI и проверить, что GitHub Release содержит оба артефакта.
- Не создавать ключи и не записывать секреты в GitHub без отдельного согласования владельца.

## Совместимость и переход

- `v0.2.15` остаётся в существующем формате без подписи; не переписывать его ради этой задачи.
- Новый механизм внедрять отдельно и поэтапно: подготовить доверенный проверяющий код и публичный ключ на приборе, затем включить подпись релизов и требование проверки.
- Предусмотреть устройства со старым установщиком, у которых нет trust store. Для них нужна документированная первоначальная процедура, а не молчаливое принятие неподписанного файла.
- Проект [обновления из UI](PLANNED-UI-UPDATE.md) в будущем должен пользоваться этим же проверяющим механизмом. Не реализовывать UI-обновление в рамках задачи подписи.

## Автоматические и аппаратные проверки

- Корректно подписанный пакет принимается известным ключом.
- Изменение одного байта пакета, подписи или неверный ключ — отказ.
- Подмена `__main__.py`, установщика, firmware или manifest — отказ.
- Отсутствующая подпись, неизвестный/revoked ключ, неверный формат и некорректная версия — отказ.
- Проверка без выполнения кода из пакета (тест на вредоносный entry point).
- Невозможность подмены файла между проверкой и установкой.
- Отказ при недоступности trust store; отсутствие неявного fallback на `--allow-unsigned`.
- Ротация ключей, совместимость со старыми устройствами и аварийная процедура.
- На реальном Raspberry Pi 5 убедиться, что проверка выполняется **до** остановки сервера/прошивки ESP32-S3 и что штатная установка/rollback не нарушены.

## Критерии готовности

1. GitHub Release публикует `.wbpkg` и соответствующую отсоединённую подпись.
2. Прибор проверяет подпись установленным заранее доверенным кодом и ключом **до исполнения скачанного пакета**.
3. Поддельный, изменённый или неподписанный пакет не устанавливается штатным путём.
4. Документированы выпуск, начальное доверие, ротация ключей, ручная установка и восстановление.
5. Тесты пройдены, полный сценарий подтверждён на реальном приборе.

**Не выпускать релиз и не включать подпись в CI автоматически при подготовке этого задания.**
