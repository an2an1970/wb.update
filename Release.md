# Release.md — выпуск пакетов WB

## Назначение

Пакет WB объединяет сервер `wb.srv` (ветка `pi`), интерфейс `wb.ui` (ветка `master`), прошивку `wb.arduino` (ветка `S3SIM`) и установщик `wb.update`. Версия пакета задаётся **только** Git-тегом в `wb.update` формата `vMAJOR.MINOR.PATCH` (например, `v0.2.10`).

## Правила

1. Обычные коммиты в любой репозиторий **не собирают пакет WB**. Workflow `Build WB Package` запускается только при push нового тега `v*.*.*` в `wb.update`. Ручного `workflow_dispatch` нет.
2. Решение выпустить пакет принимается отдельно. Не создавать тег до завершения подготовки и проверки.
3. `CHANGELOG.md` обновляется **до тега** в том же коммите, что и релизная конфигурация. Формат: одна секция на выпуск, агрегированные изменения продукта по функциям, без хронологии отдельных коммитов; пометки `(srv, ui, fw, js)`. Отдельно описывать существенные ограничения и особенности установки. Не подменять историю продукта перечнем правок установщика.
4. В `release-components.json` записаны **точные Git-теги и полные SHA** готовых релизных артефактов `wb.srv`, `wb.ui`, `wb.arduino`. Сборка проверяет, что тег каждого компонента действительно указывает на заданный SHA. Не использовать `latest`: новый релиз компонента не должен менять состав уже зафиксированного пакета.
5. `release-components.json` содержит версию без `v`. Она обязана совпадать с тегом WB, именем `wb-VERSION.wbpkg`, `manifest.json` и заголовком первой секции `CHANGELOG.md`.
6. Коммит подготовки — **один**: документация, changelog, конфигурация, необходимые изменения workflow/скриптов и тесты. Не делать промежуточных коммитов ради запуска сборки.
7. Тег указывает на проверенный коммит `main`. Сборка использует checkout именно тега; артефакт выпуска нельзя незаметно заменить. Если GitHub Release или его asset уже существует, workflow завершается с ошибкой; `--clobber` запрещён.
8. Сборка выполняет тесты, проверяет релизную конфигурацию, скачивает артефакты компонентов, собирает и проверяет `.wbpkg`, публикует GitHub Release. Описание релиза берётся из секции этого выпуска в `CHANGELOG.md`.
9. Не изменять `wb.srv`, `wb.ui` или `wb.arduino` только ради выпуска WB. Если готового артефакта нужного SHA нет — сначала отдельно подготовить релиз соответствующего компонента.
10. Сборка пакета и его публикация не означают, что он проверен на физическом приборе. Не выдавать непроверенные функции (например, получение JPEG-кадров удалённого экрана) за проверенные.

## Процедура выпуска

1. Сравнить фактические изменения `srv/ui/fw` с предыдущим выпуском, определить готовность компонентов и известные ограничения.
2. Выбрать новую версию, например `0.2.10`, и заполнить `release-components.json` точными тегами и SHA.
3. Добавить в начало `CHANGELOG.md` секцию `## Выпуск 7 ноября 2026 — версия 0.2.10` с агрегированными изменениями. Убедиться, что она описывает именно выбранные SHA.
4. Выполнить `python3 scripts/validate-release.py --tag v0.2.10` и `python3 -m unittest discover -s tests -v`. Внести все исправления **до единственного коммита**.
5. Создать один коммит на `main`. После его проверки создать и отправить тег **на этот коммит**:
   ```bash
   git fetch origin main
   git switch main
   git pull --ff-only
   git tag v0.2.10
   git push origin v0.2.10
   ```
   Перед созданием тега проверить `git status --short` (пусто), `git log -1 --oneline` и отсутствие `v0.2.10` в удалённом репозитории.
6. Дождаться единственной сборки по тегу, проверить результат workflow, GitHub Release и `manifest.json` готового пакета. Затем отдельно провести проверку установки на приборе без необязательных перепрошивок.

## Ошибки и повторные попытки

Если проверка или сборка не удалась, сначала исправить причину. Уже опубликованный тег и релиз не переписывать; для исправленного выпуска использовать новую версию. Не создавать фиктивный успешный релиз и не подавлять ошибки проверок.
